# ADR 0008: Distribute local mode through a Homebrew formula in our own tap

- Status: Accepted
- Date: 2026-11-25

## Context

Developers on macOS (and some on Linux) expect `brew install` and `brew services start` for a local mail catcher, as Mailpit offers. Phase 14d adds a Homebrew install that runs local mode as a background service with data under `$(brew --prefix)/var/mailcubby`.

Constraints found while researching GoReleaser v2.20.3 and Homebrew 7.0.15:

- GoReleaser can publish a **formula** (`brews`) or a **cask** (`homebrew_casks`). `brews` is deprecated in favour of `homebrew_casks` but still supported in v2.20.3.
- Only formulae support `brew services`. A cask's `service` stanza is a macOS Services-menu item, not a launchd agent or systemd unit.
- Casks install unsigned binaries with the `com.apple.quarantine` attribute, so Gatekeeper blocks them until the user removes it. Formulae installed from bottles or archives by `brew` are not quarantined.
- homebrew-core is not an option: it only accepts licenses it considers open source, and PolyForm Shield (ADR 0007) is not.
- Since Homebrew 6, formulae from third-party taps load only from trusted taps. `brew install mailcubby/tap/mailcubby` (fully qualified) trusts the tap automatically; `brew trust --tap mailcubby/tap` does it explicitly.

## Decision

Publish a **formula** named `mailcubby` with the GoReleaser `brews` section to the tap repository `mailcubby/homebrew-tap` (directory `Formula`).

- The formula installs the prebuilt darwin and linux (amd64, arm64) archives from GitHub Releases. Linuxbrew uses the same formula and service block (systemd user unit).
- Its `service` runs `mailcubby serve` with `MAILCUBBY_MODE=local` and `MAILCUBBY_DATA_DIR=$(brew --prefix)/var/mailcubby`, `keep_alive`, logs to `$(brew --prefix)/var/log/mailcubby.log`. `post_install` creates the data and log directories because launchd and systemd refuse to start a service whose working directory is missing.
- The service keeps the default listen addresses (`:8025`, `:1025`, all interfaces), like Mailpit and the binary itself, so Docker containers and VMs can reach it. The caveats and README say that local mode has no authentication and show the loopback-only override through `~/.homebrew/services/mailcubby.env` (`$XDG_CONFIG_HOME/homebrew/services/` when `XDG_CONFIG_HOME` is set), which `brew services` reads on every start since Homebrew 6.0.15 and keeps across upgrades. On older Homebrew users run `mailcubby serve` themselves or use the service files below.
- `skip_upload: auto`: pre-release tags do not update the tap.
- The release workflow passes `HOMEBREW_TAP_GITHUB_TOKEN` (a fine-grained token with contents write on `mailcubby/homebrew-tap` only) to the publishing step. The snapshot step does not need it.
- The Releases binary can also run as a service without Homebrew: `deploy/launchd/dev.mailcubby.plist` (macOS LaunchAgent) and `deploy/systemd/mailcubby.service` (Linux user unit), shipped in the release archives and documented in the README.

## Consequences

- `goreleaser check` exits 2 ("configuration is valid, but uses deprecated properties") because of `brews`. `goreleaser release` only prints a deprecation warning and succeeds. Nothing in CI runs `goreleaser check` today; if a check is added, it must accept exit 2 or the deprecation must be resolved first.
- Exit plan: if a GoReleaser release removes `brews`, either pin GoReleaser until then, move to a formula generated by our own small template step in `release.yml`, or switch to `homebrew_casks` if casks gain `brew services` support. Any of these needs a new ADR only if it changes what users install.
- No Apple notarization or code signing is needed for the formula. Notarization becomes necessary only if we ship a cask or a signed `.pkg`.
- Users must stop Mailpit (or anything else on 1025 or 8025) before starting the service, or change the ports in the services env file.
- The tap is outside homebrew-core, so `brew install mailcubby` without the tap prefix does not work, and Homebrew's own CI does not test the formula. The formula's `test` block (`mailcubby version`) runs only when a user or the owner runs `brew test`.
