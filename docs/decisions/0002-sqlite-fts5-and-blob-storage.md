# ADR 0002: SQLite with FTS5 for metadata and search, zstd files for raw messages

- Status: Accepted
- Date: 2026-11-23

## Context

We need durable storage for metadata, users and settings, full-text search with diacritic-insensitive matching (Portuguese and other Latin-script languages), and storage for raw messages up to 25 MiB, without requiring an external database. Typical instances hold thousands to a few million messages. Mailpit stores everything, including raw messages, in SQLite; large blobs inside SQLite inflate the database, slow vacuum and backups, and make retention deletes expensive.

Alternatives considered: PostgreSQL (extra service, against the zero-dependency goal; kept on the roadmap), Bleve or another Go search index (second storage engine to keep consistent), storing raw messages as SQLite BLOBs (simple but scales poorly), uncompressed files (2 to 5 times more disk).

## Decision

- SQLite via `modernc.org/sqlite` (pure Go, works with `CGO_ENABLED=0`), WAL mode, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`, `auto_vacuum=INCREMENTAL`. One writer connection (`_txlock=immediate`) and a read-only reader pool.
- Schema managed by goose migrations embedded in the binary; type-safe queries generated by sqlc; hand-written SQL only for dynamic search.
- Search with an FTS5 contentless table (`tokenize='unicode61 remove_diacritics 2'`, `prefix='2 3'`, `contentless_delete=1`, which needs SQLite 3.43+; modernc v1.63.0 bundles 3.54.1), inserted in the same transaction as the message row and deleted by an `AFTER DELETE` trigger on `messages` (also fired by cascades). `messages.pk` is `AUTOINCREMENT` so rowids are never reused.
- Raw messages stored unmodified as zstd-compressed files: `/data/blobs/<project_id>/<yyyy>/<mm>/<ulid>.eml.zst`. Write order: blob (temp file, fsync, rename) then DB row; delete order: row then blob; an hourly GC removes orphans.

## Consequences

- No external services; backups are a SQLite `.backup` plus a directory copy.
- Pure Go SQLite is slower than the C library for some workloads; NFR targets are set accordingly and benchmarked.
- Two storage locations must stay consistent; the write/delete ordering and orphan GC make inconsistency benign (an orphan file, never a row without a file, except after manual tampering).
- A future PostgreSQL or S3 backend needs a store/blob interface boundary, which the package layout already provides.
