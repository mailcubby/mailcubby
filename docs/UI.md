# Mailcubby: UI Specification

The web UI is a single-page app in `web/`, built by Vite and embedded in the Go binary. This document defines design principles, stack, screens and interaction details. Behaviour and permissions come from `docs/SPEC.md`; the API from `internal/api/openapi.yaml`.

## 1. Design principles

1. **Modern and calm.** Inspired by Resend and Linear: cool-tinted neutral surfaces, thin borders, one coloured chrome layer (direction "Estúdio", Phase 15), generous but dense layout. No decorative gradients and no illustrations; empty states use lucide icons only.
2. **Dense.** Developers scan many messages. Message rows keep three levels (sender, subject, snippet), about 70 px in the compact density (default) and 80 px in the comfortable one; single-line rows are a separate, later decision. Base font 13 px in lists and chrome, 14 px in reading areas.
3. **Keyboard-first.** Every action reachable by keyboard; the command palette (`Cmd/Ctrl+K`) reaches every screen and action. Mouse use is fully supported but never required.
4. **Fast.** Instant navigation from cache, prefetching, optimistic updates, skeletons instead of spinners, virtualised lists. Budget: initial JS under 250 KB gzip (SPEC NFR-009).
5. **Themes.** Light, dark and system (default). Theme applied before first paint by `/theme.js` (a static file, because inline scripts are blocked by CSP).
6. **Colour carries identity and state, not decoration.** Colour has three jobs:
   - **Chrome layer.** The top bar and sidebar sit on one deep ink-green surface (`--sidebar-*`) in both themes. In dark mode the chrome is lighter than the canvas, so it reads as a layer.
   - **Accent.** One teal accent (`--accent`, `--primary`, `--ring`) is used only for focus rings, selection (the open message, the active settings section, the chosen option), unread indicators, primary buttons, the realtime arrival highlight, and the soft `accent` badge that marks the elevated or current item in a set (the owner role, Admin, the current session, `write` token scope, an overridden instance setting). Empty-state icons, avatars and waiting states stay neutral.
   - **Semantic states.** `success`, `warning`, `info` and `destructive` mark status (alerts, status badges, the realtime dot). A status badge always carries text and a leading dot. A role badge always carries text and an icon (owner `Crown`, member `Pencil`, viewer `Eye`). Colour is never the only signal.

   Project colours appear only as small dots and the project line on the inbox list header. Content panes are neutral, and the email preview canvas is never themed. Components use only the tokens below: no raw Tailwind palette classes or hex values in `.tsx` (enforced by `web/src/styles/palette-guard.test.ts`).
7. **Typography.** Inter Variable (self-hosted via `@fontsource-variable/inter`), `font-feature-settings: "cv11", "ss01"`; `tabular-nums` for times, counts and sizes. Monospace: `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` for raw source, headers, credentials.
8. **Motion.** 120 to 180 ms ease-out for panels, popovers and arrival highlights. Disabled under `prefers-reduced-motion`.
9. **Trustworthy with untrusted content.** Email HTML only ever appears inside the sandboxed iframe (SPEC 12.1). The UI makes blocked remote content visible and opt-in.

Components (`web/src/components/ui/`): `Button` variants `primary`, `secondary`, `outline` (default), `ghost`, `destructive`, and `chrome` (ghost button on the chrome layer); `buttonClassName()` gives links the same look. Project colour tokens: `slate, red, orange, amber, lime, green, teal, cyan, blue, violet, fuchsia, pink` (12, matching SPEC FR-030).

## 2. Stack

- React 19, Vite 8, TypeScript 6 (strict), Tailwind CSS v4 (CSS-first config), shadcn/ui components (Radix-based, copied into `web/src/components/ui/`).
- TanStack Router (file-based routes, typed search params), TanStack Query (server state, SSE-driven cache updates), TanStack Virtual (message list).
- `cmdk` (command palette via shadcn `command`), `sonner` (toasts), `react-resizable-panels` (via shadcn `resizable`), `lucide-react` icons.
- Shiki (lazy-loaded, fine-grained bundle via `shiki/core` with only `html`, `css`, `json`, a custom plain theme and the JavaScript regex engine `createJavaScriptRegexEngine`; no WASM, so the app CSP needs no `wasm-unsafe-eval`) for read-only HTML source and headers highlighting. Raw sources above 512 KB are shown as virtualised plain text without highlighting. CodeMirror is not used in v1 (no editing needed).
- `openapi-fetch` typed client generated from `internal/api/openapi.yaml`.
- Exact versions: `AGENTS.md` section 3.

## 3. Screens

### 3.1 Login

Centered card: the brand mark, the instance name as the title (from `GET /api/v1/meta`, audit V6) with "Sign in to your account" under it, email, password, "Sign in" (primary button). A muted footer sits under the card on every public page (sign-in, invite, reset, setup): "Made by Fábio Ferreira at NOOP", linking to the author (x.com/fabiomlferreira) and the company (noop.pt) as plain followable links, so public instances credit the authors. When the instance name is not "Mailcubby", the footer starts with "Powered by Mailcubby" (linking to the source repository), so the product name stays visible without competing with the instance. Errors inline under the form on the `--destructive-subtle` alert (generic "Email or password is incorrect"). Rate limit shows "Too many attempts, try again in N minutes". No sign-up link (invites only). Local mode never shows this screen.

The invite and reset pages use the same centered card. An invite link that is invalid, used or expired (and invites in local mode) shows the `EmptyState` (3.4.2) inside the card: "Invitation unavailable" with one primary action (Sign in, or Go to projects when signed in). For a signed-in user whom 3.3 sends straight to their only inbox, the links out of the invite page open that inbox instead of `/`: "Go to inbox" on the unavailable card and "Back to inbox" under "Sign out to accept".

### 3.2 Setup wizard (first run, server mode)

Steps with a progress indicator; each step is a short form. The card keeps one width (672 px, wide enough for the step 5 connection details and snippets) on every step, so it never jumps between steps. Steps 1 to 3 are collected client-side and submitted together as one `POST /api/v1/setup` at the end of step 3 (a wrong token sends the user back to step 1 with the error).

The progress indicator uses short labels that never truncate (Token, Admin, Instance, Project, Connect; hidden below 640 px, numbers only): the current step on the accent tint, finished steps with a success check. Each step's main action is the primary button; Back and Skip are outline or ghost. On step 5 "Send test email" is primary until the first message arrives, then "Go to inbox" is.

1. **Setup token**: paste the token from the server log. The step lists where to find it, each command with a copy button: Docker Compose (`docker compose -f deploy/compose.server.yml logs mailcubby | grep "setup token" | tail -1`), Docker (`docker logs <container> 2>&1 | grep "setup token" | tail -1`) and the binary (the `setup token:` line in the terminal or log of `mailcubby serve`). A restart prints a new token, so the latest one wins. The "Paste the setup token" error shows only after a submit attempt and clears when the user types.
2. **Admin account**: name, email, password (strength hint, minimum 10 characters).
3. **Instance**: instance name (sent as `instance_name`); read-only checks with success/warning status pills, all from `GET /api/v1/meta`: configured `base_url` vs `window.location.origin`, SMTP public host, port and TLS mode (`none` is a warning), inbox domain (if set).
4. **First project**: name (slug auto-derived, editable). Creates the project and its first SMTP credential.
5. **Connect your app**: connection details and integration snippets (3.6.2), "Send test email" button, and a live status card. While waiting it is neutral ("Waiting for first message...", a spinner on a `--secondary` circle); when any message arrives (SSE) it becomes the success state (audit M9): `--success-subtle` card, a check on a `--surface` circle, "First message received!" with the subject and sender. "Go to inbox".

### 3.3 Projects home

In server mode a user who is neither an admin nor allowed to create projects and has exactly one project never sees this page: opening `/` (signing in without a return URL, accepting an instance invite, the logo, `g p`) replaces it with that project's inbox (SPEC FR-035, audit V1). While that decision waits for the project list (or for a refetch of a cached list that names one project), the content area stays empty (no skeleton), so the page never flashes before the inbox. A project that answers 404 (deleted, or the user was removed) is dropped from the cached list and the list is refetched, so "Back" from "Project not found" never bounces back to it. An explicit return URL after sign-in wins. Admins, users who can create projects (the page holds "New project"), users with zero or two or more projects, and local mode see the page as below.

- App header (every authenticated screen, 48 px, on the chrome layer): logo and instance name (links to this page), "Local mode" pill in local mode, "Admin" link (instance admins), then on the right "Preview as viewer" (project owners, inbox only), the search field that opens the command palette (`Cmd K`), the keyboard-shortcuts button (hidden for viewers: the effective role in a project, or outside a project a non-admin whose every project role is viewer; `?` and the palette still open the shortcuts), and the header menu. A viewer's header has at most three controls: logo, search and account menu.
- Header menu: in server mode the account menu (avatar initial and name; Profile, Security and sessions, API tokens, Preferences, Admin for admins, Theme, Sign out); in local mode a "Preferences menu" with Preferences and Theme. Theme is a Light / Dark / System radio group (`menuitemradio`); choosing one applies it and closes the menu. The theme is also in the command palette and in Account > Preferences. The sign-in, setup, invite and reset pages have no account menu and keep a small Light / Dark / System toggle in their own top bar.
- Page: title "Projects" (20 px, like the settings, account and admin titles) and "New project" (if allowed).
- Filter input ("Filter projects", `/` focuses it).
- Project list as cards in a responsive grid (or compact list, toggle remembered). Each card: colour dot, name, slug (mono, muted), role badge (owner/member/viewer), unread count (accent badge), total messages, size, "last message 3m ago", 24 h sparkline (inline SVG, 24 bars, muted colour; accent for the latest hour if non-zero).
- Realtime: counts and sparklines update via SSE; a card briefly highlights when mail arrives.
- Keyboard: arrows/`j`/`k` move focus, `Enter` opens, `n` new project.
- Local mode: a banner with "SMTP `localhost:1025`, any username creates a project" and copy buttons.
- Empty state (no projects, `EmptyState` on a dashed card): explains what a project is and offers "New project" (or, for users without permission, "Ask an admin to add you to a project"). A filter without matches shows "No matching projects" with "Clear filter"; a failed load shows "Could not load projects" with Retry.

- **Sidebar** (collapsible with `[`, on the chrome layer like the header): project switcher (project colour dot, name, popover with search, also `Cmd+K`), Inbox (count), Unread (count in an accent pill), tags with counts (click filters; `+` creates tag for members), credentials (filter by credential, owner/member only), Settings link, "Back to all projects", connection quick-copy (SMTP host/port/username) for members, and the Live indicator. Group labels are sentence case ("Tags", "Credentials", "SMTP quick copy"). "Back to all projects" and the switcher popover's "All projects" link are hidden in server mode for exactly the users that 3.3 sends straight to their inbox (no admin rights, no project creation, one project), and they render only once the user and project list have loaded, so they never flash. Below 1024 px the sidebar opens as a drawer on the same chrome surface.
- **Skip link**: the first focus stop on the inbox route is "Skip to message list", visually hidden until focused; it moves focus to the message list (the listbox, or the list pane when it is empty), so Tab, Enter reaches the list in two stops. It renders only while the list is on screen: below 768 px an open message replaces the list, and the skip link is absent there (the pane's "Back to <project>" link returns to the list).
- **Message list** (virtualised): search bar with operator autocomplete (typing `from:` suggests recent senders; `tag:` suggests tags; `is:` suggests `unread`/`read`; `has:` suggests `attachment`) and parsed operators shown as removable chips. Row content, on three levels: unread dot (accent), sender name and relative time (both bolder when unread), subject (medium weight when unread) with the attachment icon and tag pills (soft neutral `Badge` with the tag colour dot, max 2 + "+N"), and the snippet (muted, single line). States use tokens only: the open message has the `--accent-subtle` tint (no side bar), checked rows `--muted`, hover `--muted`, keyboard focus an inset 2 px `--ring` outline (the list scrolls, so an outside ring would be clipped), and a new arrival fades from `--accent-subtle` over 1.5 s. The list title ("Inbox", "Unread", a tag or credential) is 15 px semibold with the count beside it; the bulk bar sits on `--accent-subtle`. Multi-select with `x` or checkbox/shift-click; bulk bar shows delete, mark read/unread, tag. Infinite scroll with cursor pagination. Header shows total and "Delete all" (member) with confirmation that states the count and active filter. A 2 px line in the project colour runs along the top of the list pane.
- **Reading pane**: message header and tabbed views (3.5). When nothing is selected it shows an empty state (3.4.2): for owners and members "Select a message to inspect" with the `j`/`k`, `⌘K` and `?` hints; for viewers (and "Preview as viewer") the plain "No email selected. Choose an email from the list to read it." without shortcuts (audit V2); "Nothing to show" when the current filters match nothing; the setup guide when the project has no messages (3.4.1).
- Pane widths persist per user (localStorage). Below 1024 px the layout becomes two panes (sidebar collapses into a drawer); below 768 px it becomes a single stacked view with back navigation.

#### 3.4.1 Empty inbox = setup guide

For a project with zero messages, "No messages yet" appears once (audit M6). The reading pane holds it: an empty state with the title, one line ("Point your app's SMTP client at Mailcubby, or send a sample message now.") and a primary "Send test email" button (member+; calls `POST /send-test`), followed by the connection details (host, port, TLS, username; password reveal for allowed roles), recipient routing addresses if enabled, and the integration snippet tabs (3.6.2). Viewers see only the empty state "No messages yet" with "Emails sent to <project> appear here as they arrive." The list pane meanwhile shows a compact "Waiting for mail" state. Below 768 px there is no reading pane, so the list shows the "No messages yet" empty state itself, with "Send test email" for members and owners.

#### 3.4.2 Empty states

Every empty, error and not-found state uses one component, `EmptyState` (`web/src/components/EmptyState.tsx`): a lucide icon on a neutral tinted circle (`--secondary`, decorative and `aria-hidden`), a title (an `h1` for a full page, `h2` for a pane, `h3` inside a card), one line of help text, and at most one action (Back and Retry may sit side by side on an error page). It has a compact size for the message list. The tint stays neutral because the accent is reserved for its 1.6 roles. Inbox uses:

| Pane | Title | Action |
|---|---|---|
| List, project empty (reading pane visible) | Waiting for mail | none |
| List, project empty (below 768 px) | No messages yet | Send test email (member+) |
| List, search or tag/credential filter with no results | No matching messages | Clear filters |
| List, Unread filter with nothing unread | No unread messages | none |
| Reading pane, project empty | No messages yet (+ setup guide for member+) | Send test email (member+) |
| Reading pane, nothing selected | Select a message to inspect (+ keyboard hints); viewers: No email selected | none |
| Reading pane, filters match nothing | Nothing to show | none |
| Reading pane, message missing | Message not found | Retry (load errors only) |
| Attachments tab, no parts | No attachments | none |

Elsewhere (audit V7), page-level states are centred in the content area under the app header (`web/src/components/PageStates.tsx`), and card states sit in the card body:

| Where | Title | Action |
|---|---|---|
| Unknown address (router default) | Page not found | Back to projects |
| Inbox or settings, project 404 | Project not found or you do not have access | Back to projects |
| Inbox or settings, project load error | Could not load project | Back to projects, Retry |
| Project settings for a viewer | Settings unavailable | Back to <project> |
| Projects home | No projects yet / No matching projects / Could not load projects | New project / Clear filter / Retry |
| SMTP credentials card | No SMTP credentials yet | Create first credential (owners) |
| API tokens card | No API tokens yet (or Could not load API tokens) | Create first token (or Retry) |
| Project audit log, not an owner or local mode | Audit log unavailable | none |
| Invite page | Invitation unavailable, Too many requests, Invitations unavailable (local mode) | Sign in or Go to projects |

"Back to projects" (in these states and in the account pages) reads "Back to inbox" and opens that inbox for the users that 3.3 sends straight to their only project; it never points at the project that just failed to load.

### 3.5 Message view

**Header** (on `--surface`, 16/24 px padding): the subject (18 px semibold, selectable, copy on click) with the action icon group on the same row: previous/next, mark unread, download `.eml`, copy link to message, open preview in new window (opens `/render/...` directly, still sandboxed by CSP), delete. Below it a 36 px sender avatar (up to two initials on the neutral `--secondary` tint; decorative, `aria-hidden`, "?" without a sender) beside from (name + address; click copies address) and to/cc/bcc (collapsed after 3 with "+N"), with the received time (relative, exact on hover) and size on the right. The last row holds the credential chip ("via <label>" with a key icon, neutral pill; hidden for viewers) and the tags (soft pills with the tag colour dot, editable inline for members with autocomplete; "Add tag" is a dashed pill).

**Tabs and toolbar**: the tab row is the pane's primary navigation (40 px, 13 px medium, accent underline on the selected tab). The preview toolbar sits below it on the canvas, not on a bar of its own, with 12 px controls: the device segmented control on a `--muted` track, the zoom select, ghost toggles for rotate and "Email dark" (secondary fill when on), and the remote-images notice. The preview frame is a 12 px rounded, bordered card on the canvas; the iframe inside it is unchanged.

**Tabs** (number keys `1` to `7`; `8` is reserved for a future Links tab):

| Key | Tab | Content |
|---|---|---|
| 1 | Preview | Sandboxed iframe of `/render/{project}/{id}`. Toolbar: device (desktop fluid, tablet 768 x 1024, mobile 375 x 667), rotate (swaps width/height for tablet/mobile), zoom (50 to 200%, fit), email dark-mode toggle (sets `color-scheme: dark` on the iframe element so the email's `prefers-color-scheme: dark` rules apply), remote images toggle with "N remote images blocked" notice (when `opt-in`). Device frame is a subtle rounded border with dimensions label. Hidden if the message has no HTML. |
| 2 | Text | Text part in a readable column (max 80ch), URLs auto-linked as React elements (`target=_blank rel="noopener noreferrer"`). Shows "Generated from HTML" note if `text_generated`. |
| 3 | HTML source | Highlighted (Shiki, lazy) with line numbers, wrap toggle, copy, search within (`Cmd+F` handled by browser). |
| 4 | Headers | Table of headers in original order, monospace values, copy per row, filter box. |
| 5 | Raw | Full raw source (`/raw`), virtualised plain text for large messages, copy, download `.eml`. |
| 6 | Attachments | List with icon by type, filename, size, content type, inline/attachment badge, `cid:` Content-ID, a "shown in preview" badge for parts the HTML preview inlines (`referenced_by_html`), download; thumbnails for raster images (`?inline=1`); every other type, including PDF, is downloaded. Count badge on tab (counts every part). |
| 7 | Tech | Envelope (MAIL FROM, RCPT TO), remote IP, HELO, TLS yes/no, AUTH user, credential, Message-ID, Date header vs received time, raw size, parse warnings. |

Viewers with `viewer_hide_technical` see only Preview, Text and Attachments. The last selected tab and device are remembered.

**Attachment strip** (FR-072): while Preview or Text is active, a compact strip sits below the view (a non-scrolling footer of the reading pane, so it stays visible under the full-height preview iframe without scrolling the email). Header "N attachments" with a paperclip icon, then one card per attachment (224 px, bordered, on `--surface`, a trailing download icon, hover `--muted`): thumbnail for the inline-allowlisted raster images (png, jpeg, gif, webp via `?inline=1`; never SVG), otherwise a lucide icon by type (image, PDF, calendar, archive, audio, video, text, generic file); filename (truncated, full name on hover) and size (`Intl`). Each card is a link that downloads the file (`Content-Disposition: attachment`) with the accessible name "Download <filename> <size>"; PDFs are never rendered inline. Cards wrap and the strip is capped at about two rows with its own scroll, so many attachments cannot squeeze the preview. Parts with `referenced_by_html` (inline images the preview already shows through `cid:`) are left out; the strip is hidden when no card remains. The strip is not shown on the technical tabs or on Attachments, which keeps the full details. Viewers with `viewer_hide_technical` see the strip and the Attachments tab.

### 3.6 Project settings

Left nav of sections; each section saves independently with optimistic UI and toast confirmation. Owner-only sections are hidden for other roles.

Layout (shared with account and admin pages through `SettingsShell`, `web/src/components/SettingsShell.tsx`): a "Back to <project>" link, then the page title (20 px; for projects the colour dot, the name and its `RoleBadge`) with a one-line subtitle and, on the right, the page's main action (at most one primary button per screen). Below it, a 200 px section nav (34 px items, lucide icon, the active item on `--accent-subtle`; a horizontal scroller under 768 px) beside the content column, at most 1024 px wide (1152 px for admin). Content sits in `Card`s (`web/src/components/ui/card.tsx`: 12 px radius, `--surface`, hairline border, 16 px between cards; `CardHeader` title 15 px semibold, description 13 px muted, actions on the right; `CardContent` with 20 px padding; `CardFooter` on a `--muted` strip for a form's Reset and Save, with Save primary). Every form card (general, retention, profile, change password, instance settings) ends in a `CardFooter`. Refresh actions sit in the page header (project audit log, admin audit log, stats). Tables use `web/src/components/ui/table.tsx`: 12 px sentence-case headers on `--muted`, 13 px rows with hairline dividers, 20 px outer padding aligned with the card header. Selects are native `<select>`s styled like inputs (`NativeSelect`, audit M11) and on/off settings use `Switch` (`web/src/components/ui/switch.tsx`): a native checkbox with `role="switch"` that is itself the track (so it keeps native keyboard, label and the focus ring), with the knob drawn by a sibling element rather than a pseudo-element of the input (pseudo-elements on form controls are not reliable outside Chromium). Empty states inside a card use `EmptyState` with an `h3` title (3.4.2).

#### 3.6.1 General
Name, slug (with a warning that recipient routing addresses change; shows old and new addresses), colour picker (12 tokens). Danger zone: delete project (type the slug to confirm).

#### 3.6.2 SMTP
- Connection card: host, port, TLS mode, each with copy button.
- Credentials table: label (with "Created <time>" under it), username (mono, copy), password (masked; **Reveal** (owner, or member if allowed) fetches and shows for 30 s then re-masks; **Copy** reveals and copies without displaying), status badge (with "Used <time>" or "Never used" under it). Row actions are icon buttons with an accessible name and a tooltip (`title`): rename, rotate (confirm: "Apps using the old password will fail"), disable/enable, delete. The table has a fixed layout (`table-fixed` with column widths; long labels, usernames and passwords truncate with the full value on hover), so it never overflows horizontally at 1024 px and wider (audit M1, e2e); below that the card scrolls horizontally. "New credential" (primary, owner only, in the card header) asks for a label and shows the password once with copy; with no credentials the empty state's "Create first credential" is the primary button instead.
- **Integration snippets** (tabs; values filled with the selected credential; password shown as `********` until revealed, copy button copies the real value after reveal):
  - Laravel `.env`:
    ```
    MAIL_MAILER=smtp
    MAIL_SCHEME=smtp            # Laravel 10 and older: MAIL_ENCRYPTION=tls
    MAIL_HOST=mail.example.com
    MAIL_PORT=587
    MAIL_USERNAME=shop-a1b2c3d4
    MAIL_PASSWORD=********
    ```
  - Symfony: `MAILER_DSN=smtp://shop-a1b2c3d4:********@mail.example.com:587`
  - Node.js Nodemailer: `nodemailer.createTransport({ host: "mail.example.com", port: 587, secure: false, requireTLS: true, auth: { user: "shop-a1b2c3d4", pass: "********" } })`
  - WordPress (WP Mail SMTP plugin): settings table (Mailer "Other SMTP", host, encryption TLS, port 587, auto TLS on, authentication on, username, password) and the `wp-config.php` constants alternative (`WPMS_ON`, `WPMS_MAILER`, `WPMS_SMTP_HOST`, `WPMS_SMTP_PORT`, `WPMS_SSL`, `WPMS_SMTP_AUTH`, `WPMS_SMTP_USER`, `WPMS_SMTP_PASS`, `WPMS_SMTP_AUTOTLS`).
  - Django `settings.py`: `EMAIL_BACKEND`, `EMAIL_HOST`, `EMAIL_PORT = 587`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS = True`.
  - Rails: `config.action_mailer.delivery_method = :smtp` and `smtp_settings` with `address`, `port: 587`, `user_name`, `password`, `authentication: :plain`, `enable_starttls_auto: true`.
  - swaks: `swaks --to test@example.com --server mail.example.com:587 --tls --auth PLAIN --auth-user shop-a1b2c3d4 --auth-password '********'`
  - PHP `sendmail_path`: `sendmail_path = "/usr/local/bin/mailcubby sendmail -t"` (local mode).
  In local mode snippets use the `smtp` host and port from `GET /api/v1/meta` (defaults `localhost`, `1025`), no TLS, and the project slug as username with a placeholder password. Snippet generation is a pure function (`web/src/features/settings/snippets.ts`) so it can be golden-tested.

#### 3.6.3 Members and invites
Subtitle per role (audit M5): owners read "Manage who has access to this project and share invite links."; members read "People with access to <project>.". Owners get the page's primary action **Invite people** in the header (audit M7), which opens the "Invite" dialog: email + role (viewer by default, with a line explaining the role); the result shows the invite link with copy button and "Link shown once" note. Members table (name with a "You" badge, email, role, joined, remove): owners change roles with a select styled like the inputs (audit M11); everyone else sees the role as a `RoleBadge`. Invites table (owners only; email, invited by, role badge, status badge, expires, revoke): status badges carry a dot, pending = warning, accepted = success, expired and revoked = neutral (audit M3). By default it lists only pending invites, since accepted ones are already in the members table (audit M4); a **Show accepted** checkbox in the card header (shown when any invite is not pending) lists every invite the API returns, including revoked and expired ones. With none pending the card reads "No pending invites.". "Preview as viewer" toggle explained here (3.8).

#### 3.6.4 Retention
Max age, max messages, max size: each with "Inherit instance default (30 days)" checkbox or a value. Shows current usage (messages, size) against limits with a simple bar.

#### 3.6.5 Routing and client view
Recipient routing toggle (server mode) with the resulting addresses (`*@shop.inbox.example.com`, `shop+tag@inbox.example.com`) and a warning that unauthenticated senders can then write into this project. Plus-addressing tags toggle. "Hide technical views from viewers" toggle. "Members can reveal SMTP passwords" toggle.

#### 3.6.6 API
Explains API tokens (created in Account > API tokens, optionally restricted to this project), with a "Create token for this project" shortcut and copyable `curl` examples for list, wait and delete-all using the project slug.

### 3.7 Account and admin

- **Account**: profile ("Account details" card: name, email read-only), security (change password, active sessions with revoke), API tokens (create with name, scope, project, expiry; token shown once), preferences (theme, density, mark-as-read delay 0/1/3 s/never, single-key shortcuts on/off, 24 h clock), followed by an "About Mailcubby" card (version from `GET /api/v1/meta`, "Made by Fábio Ferreira at NOOP" and the licence link). Preferences are per browser (`usePersistentState`, localStorage), not stored on the server. In local mode only `/account/preferences` exists (reachable from the header "Preferences menu" and the palette); the other account sections are server-mode only. Theme is also switchable from the header menu (3.3).
- **Admin**: Users (table, search, invite user, toggle admin / can-create-projects, disable, reset link), Projects (all projects with owners, counters, open), Settings (instance name, default retention with "from env" vs "overridden" indicator), Audit log (filterable table: time, actor, action, project, target, IP; JSON metadata on expand), Stats (cards: messages, storage, DB size, ingest rate, version, uptime).
- Account and admin pages use the same frame and components as project settings (3.6): `SettingsShell` with "Back to projects", the section nav, `Card`, the table primitives, `NativeSelect` and `Switch` (admin user toggles, preference toggles). Each page has at most one primary button: Save profile, Update password, New API token (Create first token when there are none), Invite user, Save settings. The project settings API section's "Create token for this project" link uses the primary button look (`buttonClassName`).

### 3.8 Client view mode

Viewers get a simplified UI: no delete or tag actions, no SMTP or settings sections, technical tabs hidden when `viewer_hide_technical` is on, and a clean header with only the logo, search and the account menu (no shortcuts button; 3.3). Owners can toggle **Preview as viewer** (eye icon in the header, also in the palette) to see exactly what viewers see, header included; a persistent banner shows while active.

## 4. Premium details (required for v1)

1. **Command palette** (`Cmd/Ctrl+K`): fuzzy search over projects, tags, actions ("Delete all in shop", "Copy SMTP password", "Toggle theme", "Go to settings", "Send test email"), recent messages by subject, and search operators. Grouped results, keyboard only, shows shortcuts next to actions, remembers recent commands. Follows the Superhuman command palette guidance (reference 3).
2. **Keyboard shortcuts** (single-key shortcuts are disabled while focus is in an input, and can be turned off in preferences, WCAG 2.1.4):

   | Key | Action |
   |---|---|
   | `j` / `k` | next / previous message (opens it in the reading pane) |
   | `Enter` / `o` | open focused message / focus reading pane |
   | `Esc` | close dialog, clear selection, back to list |
   | `e` or `#` or `Delete` | delete message (with undo) |
   | `u` | toggle read / unread |
   | `x` | select message; `Shift+j/k` extends selection |
   | `/` | focus search |
   | `t` | edit tags |
   | `1` to `7` | switch message tab (`8` reserved) |
   | `d` | cycle device (desktop, tablet, mobile) |
   | `i` | toggle remote images |
   | `[` | toggle sidebar |
   | `g p` / `g s` / `g a` | go to projects / project settings / account |
   | `Cmd/Ctrl+K` | command palette |
   | `?` | shortcuts help overlay |
3. **Realtime arrival**: new messages slide into the list with a 1.5 s accent background fade; if the list is scrolled down, a "N new" pill appears at the top (click scrolls up); the document title shows the unread count (`(3) shop - Mailcubby`); an `aria-live="polite"` region announces "New message from Alice: Order #123" (throttled to one announcement per 5 s).
4. **Empty inbox as setup guide** with "Send test email" (3.4.1).
5. **Optimistic delete with undo**: the row disappears immediately; a toast "Message deleted. Undo" stays 5 s; the API call is sent when the toast expires (or immediately on `pagehide` using `fetch(..., { keepalive: true })`). Bulk deletes and delete-all use a confirmation dialog instead of undo.
6. **Skeletons** for list rows, message header and project cards; no full-page spinners. Content appears from cache instantly when available. One exception: while the projects home waits for the project list of a user it may send straight to their inbox (3.3), the content area stays empty (`aria-busy`) instead of showing the project card skeleton. That wait lasts one request, and a skeleton there would show the projects page for a moment before the inbox replaces it (the flash recorded in Phase 15c); users who stay on the page (admins, project creators, local mode) still get the skeleton.
7. **Prefetch**: when a message opens, prefetch the next and previous message details; prefetch on 100 ms row hover; prefetch the render URL of the next message only on fast connections (`navigator.connection.saveData` false).
8. **Device preview** with rotation, zoom and email dark-mode toggle (3.5).
9. **Remote image toggle** with a blocked-count notice; per message, not persisted (privacy).
10. **Copy on click** for addresses, Message-ID, SMTP fields, slugs and snippets, with a short "Copied" toast.
11. **Relative timestamps** (`now`, `3m`, `2h`, `Yesterday 14:03`, `12 Nov`) via `Intl.RelativeTimeFormat` / `Intl.DateTimeFormat`, updating every minute; exact local and UTC time in a tooltip on hover/focus.
12. **Client view mode** (3.8).
13. **Remembered layout**: pane widths, sidebar collapsed state, selected tab, device, density, theme (localStorage, namespaced `mailcubby:`).
14. **Connection state**: a small indicator in the sidebar footer shows realtime status (connected, reconnecting); on reconnect the app invalidates queries.
15. **Error handling**: API errors show toasts with the server message; `401` redirects to login preserving the return URL; `404` on a project shows "Project not found or you do not have access"; any other failure to load a project shows "Could not load project" with a way back and Retry, except on the only project of a user whom 3.3 sends straight to their inbox, where every way back leads to the same project, so "Try again" (refetch) is the one, primary action; an unknown address shows "Page not found" inside the app shell (3.4.2).

## 5. Accessibility (WCAG 2.1 AA)

- Contrast: text 4.5:1, large text and UI components 3:1, in both themes (verified with axe in e2e and by the computed token table `docs/ui-contrast.md`).
- Full keyboard operation; visible focus ring (2 px `--ring` outline with offset, `--sidebar-ring` on the chrome layer) on every interactive element; logical tab order; a "Skip to message list" link is the first focus stop on the inbox (3.4); focus is trapped in dialogs and restored on close.
- Message list uses `role="listbox"` (or `grid` when bulk selection is active) with `aria-selected`, `aria-activedescendant` and row labels ("Unread. From Alice. Order #123. 2 minutes ago. 1 attachment").
- The preview iframe has `title="Email preview: <subject>"`.
- Single-key shortcuts can be turned off (2.1.4); shortcuts never fire inside text inputs.
- `aria-live` announcements for new mail and for toasts (sonner supports this).
- Respect `prefers-reduced-motion` and `prefers-contrast`; support 200% zoom and 320 px width without loss of content.
- Icons that convey meaning have labels; colour is never the only signal (unread uses dot + bold weight; project colours accompany names).
- Forms: labels bound to inputs, errors linked via `aria-describedby`, required fields marked.
